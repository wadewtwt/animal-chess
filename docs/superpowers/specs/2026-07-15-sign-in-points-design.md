# 动物棋签到积分设计

## 1. 目标

为 `animal-chess` 小游戏增加“微信身份登录 + 每日签到 + 积分累计 + 签到成功庆祝动画”能力，覆盖前后端联动。

本次只实现：

- 微信小程序 `code` 登录
- 每日固定 `+10` 积分签到
- 主菜单首页自动弹出签到面板
- 签到成功后播放恭喜动画
- 按周周期统计签到表现

本次不实现：

- 补签
- 签到额外奖励
- 积分商城
- 排行榜
- 任务系统

## 2. 已确认业务规则

- 用户身份以微信小程序登录为准，后端按 `openid` 建立本地用户，预留 `unionid`
- 表名前缀统一使用 `animal_chess_`
- 每日签到奖励固定为 `10` 积分
- 连续签到不影响加分，只做展示
- 签到入口放在主菜单首页
- 用户进入主菜单时，如果当天未签到，自动弹出签到面板
- 签到成功后展示“签到成功恭喜动画”
- 签到统计按自然周计算，周一 `00:00` 重置新周期

## 3. 周期口径

### 3.1 周期定义

- 每周一 `00:00:00` 到周日 `23:59:59` 为一个签到周期
- 每个周期最多可签到 7 次

### 3.2 展示字段

前端展示两类信息：

- `本周已签到 X/7 天`
- `本周连续签到 Y 天`

### 3.3 本周连续签到规则

- 本周第一次签到后，`本周连续签到天数 = 1`
- 如果用户昨天已签到，今天再签到，则 `本周连续签到天数 +1`
- 如果用户昨天未签到，则今天签到后重置为 `1`
- 到下周一后，不继承上周连续值，新周重新开始

## 4. 整体方案

采用“`animal-chess-server` 内新增轻量 HTTP 业务接口 + 保留现有 WebSocket 对局服务”的方案。

原因：

- 现有服务端已经负责对局和房间同步，不适合把登录与积分逻辑塞进 WebSocket 指令流
- 旧项目 `my-blog-gin` 中已有微信 `code` 登录链路，可以复用设计思路、字段和错误处理风格
- 登录、签到、积分适合走 HTTP API；实时对局继续走 WebSocket，边界清晰

## 5. 前端设计

### 5.1 入口位置

在主菜单首页增加：

- 积分展示入口
- 自动弹出的签到面板

入口职责：

- 展示当前总积分
- 进入主菜单时触发登录检查与签到状态检查

### 5.2 进入主菜单流程

1. 进入主菜单
2. 检查本地是否已有业务 `token`
3. 如果没有，调用微信 `wx.login()` 获取 `code`
4. 使用 `code` 调用后端登录接口，换取业务 `token`
5. 调用签到状态接口
6. 如果今天未签到，自动弹出签到面板

### 5.3 签到面板内容

- 今日签到状态
- 当前总积分
- 本周已签到天数
- 本周连续签到天数
- 最近 7 天签到轨迹
- 立即签到按钮

### 5.4 立即签到交互

- 点击后按钮进入禁用态，防止重复点击
- 请求成功后刷新主菜单积分与签到状态
- 如果服务端返回今日已签到，则直接更新面板状态，不播放奖励动画
- 如果服务端返回首次签到成功，则播放庆祝动画

### 5.5 签到成功动画

整体风格延续现有主菜单森林童话感，不使用后台风弹窗。

建议动画表现：

- 居中弹出签到徽章或木牌
- 主文案：`签到成功`
- 副文案：`+10 积分`
- 附带金色粒子、星点扩散、轻微发光和缩放回弹
- 总时长控制在 `1 ~ 1.5` 秒
- 结束后自动淡出，不阻断继续操作

## 6. 后端设计

### 6.1 接口规划

- `POST /api/auth/wx/login`
- `GET /api/sign-in/status`
- `POST /api/sign-in`
- `GET /api/points/summary`

### 6.2 微信登录接口

请求：

- `code`

处理逻辑：

1. 服务端调用微信 `jscode2session`
2. 获取 `openid`、`unionid`
3. 查询本地用户
4. 不存在则创建
5. 存在则更新最近登录时间及必要资料
6. 返回业务 `token` 和用户摘要

说明：

- 复用 `wt-blog-main/my-blog-gin` 的微信登录设计思路
- 不直接复用其运行时代码

### 6.3 签到状态接口

返回内容建议包含：

- `signedToday`
- `totalPoints`
- `weekSignedDays`
- `weekContinuousDays`
- `lastSignInDate`
- `recent7Days`

### 6.4 执行签到接口

处理逻辑：

1. 校验用户登录态
2. 计算当前自然周的起始日期 `week_start_date`
3. 校验今天是否已签到
4. 未签到则开启事务
5. 写入签到记录
6. 写入积分流水
7. 更新用户总积分、本周连续签到天数、最后签到日期
8. 返回最新积分和签到结果

## 8. 并发与幂等设计

本次必须具备防并发校验机制。

采用四层保护：

### 8.1 前端防重

- 签到按钮点击后立即禁用
- 接口返回前不可重复点击

### 8.2 服务端业务校验

- 进入签到接口时先校验今日是否已签到

### 8.3 数据库唯一约束

- `animal_chess_sign_in_record` 使用唯一索引 `(user_id, sign_in_date)`
- 即使两个并发请求同时通过前置校验，也只能有一个真正插入成功

### 8.4 事务保证

以下步骤必须放在同一个事务中：

- 插入签到记录
- 插入积分流水
- 更新用户总积分
- 更新用户最后签到日期
- 更新本周连续签到天数

并发失败时的处理要求：

- 若命中唯一索引冲突，返回“今日已签到”
- 不允许重复加分
- 不返回 500 作为正常重复签到结果

## 9. 异常处理

### 9.1 服务端

- 微信 `code` 无效：返回登录失败或未授权
- `token` 无效：返回未登录
- 今日重复签到：返回已签到状态
- 数据库事务失败：记录 error 日志并返回签到失败

### 9.2 前端

- 登录失败：提示“登录失败，请稍后重试”
- 拉取签到状态失败：不阻断主菜单进入，但不自动弹签到面板
- 签到失败：保留签到面板，允许重试

## 10. 日志要求

遵守当前项目规则：

- 阻断并直接 `return` 前先记日志
- `throw` 或返回严重错误前先记 `error` 日志
- `error` 日志格式：`类名 + 方法名 + error + 具体信息`

建议重点日志点：

- 微信登录失败
- 签到重复提交
- 签到事务失败
- 积分更新失败

## 12. 验收标准

1. 微信小游戏进入主菜单时，未登录用户可自动完成登录并拉取签到状态
2. 当天未签到时，主菜单会自动弹出签到面板
3. 点击签到后，只能成功入账一次，积分固定增加 `10`
4. 同一天并发或重复请求签到，不会重复加分
5. 本周连续签到天数按“周一重置”规则正确计算
6. 本周已签到天数展示正确
7. 签到成功后主菜单积分刷新，并展示签到成功恭喜动画
8. 登录失败、签到失败、重复签到时都有明确反馈，且服务端有对应日志
